# Codex Sessions v0.3.1 Design Review

Reviewed: 2026-08-16

## Scope and method

This review evaluates the shipped `v0.3.1` product from a user's perspective, not whether the code
matches its implementation plan. Evidence came from:

- walking the complete install → index → browse → search → enrich → delete → recover tutorial;
- the published CLI help and installed `Codex Sessions 0.3.1` binary;
- current README and user documents;
- focused inspection of the TUI footer, background warm, enrichment budgeting, deletion, and
  recovery paths;
- concrete dogfood questions raised while using the product.

The review does not assume that more features are better. A personal, local-first tool benefits
from a small scope, and deferred features are treated as defects only when current behavior creates
observable failure or repeated confusion.

## Overall assessment

The core architecture is sound and should not be rewritten. Native JSONL authority, a disposable
redacted index, on-demand masked preview, an explicit network boundary, and fail-closed deletion
reconciliation fit the product unusually well. The highest-value work is interaction refinement,
not a new storage model, semantic-search stack, cloud service, or framework migration.

The main weakness is that several technically safe behaviors are described with UI language that
does not match the user's mental model. In particular, “delete” means two different things, a
soft-deleted item has no targeted restore path, and a complete background scan does not currently
give `resume` the same deletion reconciliation behavior as explicit `reindex`.

## What is already well designed

### Native source of truth

Keeping `~/.codex/sessions` authoritative and treating SQLite as disposable makes recovery and
rollback understandable. It avoids a second transcript store and lets parser/index changes rebuild
derived state safely.

### Privacy and network boundary

Normal browse, search, preview, resume, and reindex paths are network-free. Live enrichment is a
separate explicit action with `--yes`, redaction, bounded input, `store: false`, and no tools. This
is a better default than automatic summarization for a session browser that may contain operational
or VPS content.

### Fail-closed reconciliation

`v0.3.1` distinguishes an empty native inventory from a failed or partial scan and deletes session,
FTS, and AI-derived rows atomically only after a complete inventory. This is proportionate data
integrity design, not unnecessary complexity.

### Project-aware enrichment

Defaulting enrichment to the current project and requiring explicit `--all` matches command-line
intent and prevents a bounded batch from silently being spent on unrelated recent sessions.

### Deliberate deferrals

Flat project grouping, bilingual FTS, optional AI metadata, Linux/WSL-only support, and no account or
cloud system are reasonable for the current personal-first scope. None warrants expansion without
dogfood evidence.

## Detailed interpretation

### The footer issue is a real defect, not a feature request

The product explicitly targets 80x24 SSH terminals. A test that only calls `View()` proves the
renderer does not panic, not that the footer remains on one line. Fixing this should be a small
patch release with a visible-width assertion. It does not justify redesigning the TUI.

### Soft-delete safety is good; its recovery UX is not

The tombstone prevents an incremental reindex from immediately resurrecting something the user
chose to hide. That behavior is correct. The mismatch is calling it `delete` while the confirmation
and recovery model are “hide permanently from this derived index until global reset.” A targeted
restore is more valuable than favorites, folders, or archive management because it completes an
existing action rather than introducing a new organizational system.

### Automatic reconciliation is acceptable only because the safety contract now exists

Before v0.3.1, reconciling during background warm would have risked treating scan failure as mass
deletion. With explicit per-provider completeness and partial-scan errors, the foreground logic can
be reused safely. The remaining design work is lifecycle and refresh behavior, not deletion
inference.

### Enrichment complexity is mostly justified but under-explained

Per-session truncation, total input budget, candidate limit, source fingerprints, project scope,
and explicit confirmation each protect privacy, correctness, or bounded work. Removing them would
make the system worse. The design problem is observability: the command should explain which guard
stopped a batch instead of requiring the user to reconstruct the pipeline from flag defaults.

### Directory-tree navigation is not yet proven necessary

The user's initial request for subtree collection came partly from an incorrect assumption that
Codex stores sessions inside each project's `.codex` directory. Once the global native store and
recorded `cwd` model are understood, a flat recent-project list plus filtering may be sufficient.
The tutorial should be tested before committing to tree UI complexity.

## Recommended next sequence

1. Use the new tutorial with the published binary and note where instructions still need
   explanation.
2. Ship a small reliability/UX patch for responsive 80-column footers, including a real width
   assertion.
3. Decide the semantics and UI for targeted tombstone restore; keep native files untouched.
4. If stale rows after `/delete` remain a recurring annoyance, reuse v0.3.1 reconciliation after a
   complete background warm.
5. Improve enrichment summary reasons and safe configuration diagnostics.
6. Re-evaluate tree navigation, semantic search, and token-accounting work only from new evidence.

## Conclusion

Codex Sessions is not suffering from a flawed core design. It has a strong safety model wrapped in
an interface that occasionally exposes implementation terminology instead of user intent. The
objective priority is to finish the recovery and narrow-terminal UX of features that already
exist. Expanding into semantic search, automatic enrichment, cloud, or complex organization now
would be premature.
